## [2026-08-19] Bug fix: `run_kotlin_conformance` OOM-abort killed before printing report

### Symptom (user-reported)
`cargo test -p kap-core --test conformance` died with `signal: 9, SIGKILL`
and printed NO conformance report, even though `curated_kap_parity` passed.
The full harness is FAILED-by-design (ends in an intentional `panic!`), but it
MUST still print the coverage report + non-conforming list first. The SIGKILL
meant it died *mid-loop*, before the report was written.

### Root cause (found by brute-force probing all 2535 corpus cases under a
per-case memory cap)
Exactly **one** case aborted: `2.0 3.0 ⍸ 1.5 2.0 2.0001 2.9999 3.0 3.0001 1e100`
— dyadic `⍸` (interval form). My `where_fn` ignored the left arg and treated
the right as monadic WHERE. The right contains `1e100` (Double); Rust's
`f64::as_long()` **saturates** `1e100` to `i64::MAX` (~9.2e18), so
`vec![_; 9e18]` (scalar branch) / `for _ in 0..9e18` (rank-1 branch) requested a
runaway allocation → allocator abort (`SIGKILL`/`SIGABRT`, uncatchable by
`catch_unwind`). One abort kills the whole test binary before the summary prints.

### Fix (`kap-core/src/evaluator.rs`)
1. **Dyadic `⍸` is out-of-scope** → return a clean error when `left_val.is_some()`
   (`"dyadic ⍸ (interval form) is not implemented yet"`), so the harness counts
   it Unsupported instead of aborting. Wired in the `⍸`/`where` dispatch arm.
2. **OOM guard** (per strategy, mandated for resize/take/drop): reject when the
   element count / accumulated result exceeds `100_000_000` *before* allocating —
   in both the scalar branch (`v as usize > 100_000_000`) and the rank-1 loop
   (`(out.len()+n) > 100_000_000`). Also covers monadic `⍸ 1e100`.

## [2026-08-19] `⍸` interval form (dyadic) implemented — supersedes the OOM-dodge hack

The earlier session ducked dyadic `⍸` with a "not implemented" error + a 100M
allocation guard. That was the wrong layer: as the user pointed out, `1e100` in
the right arg is a *value being compared*, never an allocation count. The
interval form `a ⍸ b` is inherently bounded by `⍴b` (Kotlin's lazy
`IntervalValue`), so a huge element like `1e100` just compares `> 3.0` →
index `2`, with no runaway.

### Implemented (faithful to Kotlin `WhereAPLFunction`/`IntervalValue`)
- New `Engine::interval(left, right)` in `kap-core/src/evaluator.rs`:
  - `a` = boundaries (scalar or 1-D vector, or string). Must be strictly
    ascending (validated via `APLValue::total_cmp`); non-ordered →
    `error: Left argument must be ordered`.
  - `b` = data. Result has the **same shape** as `b`; each element = count of
    boundaries `<=` that data value (binary search, `total_cmp`).
  - `⍬ ⍸ b` → all zeros; empty `b` (incl `⍸ ⍬` / `⍸ ""`) → `⍬`.
  - Works across number/char/**nested-array** kinds via the new cross-kind
    `APLValue::total_cmp` (mirrors Kotlin `compareTotalOrdering`).
- New `APLValue::total_cmp` in `kap-core/src/lib.rs` — numbers numerically,
  chars by codepoint, arrays recursively, otherwise by Kap `typeSortOrder`
  (number < char < array < null). Used by the interval binary search.
- Dispatch arm `⍸`/`where` now routes `Some(l)` → `self.interval(l, right_val)`
  (was the "not implemented" error).
- **Removed the 100M-element guard** from `where_fn` — it was only masking the
  dyadic bug; the monadic where count is a real allocation size and stays
  modest. (Keep the take/drop & reshape guards; those are genuine size caps.)

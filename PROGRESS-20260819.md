## [2026-08-19] Bug fix: `run_kotlin_conformance` OOM-abort killed before printing report

### Symptom (user-reported)
`cargo test -p kap-core --test conformance` died with `signal: 9, SIGKILL`
and printed NO conformance report, even though `curated_kap_parity` passed.
The full harness is FAILED-by-design (ends in an intentional `panic!`), but it
MUST still print the coverage report + non-conforming list first. The SIGKILL
meant it died *mid-loop*, before the report was written.

### Root cause (found by brute-force probing all 2535 corpus cases under a
per-case memory cap)
Exactly **one** case aborted: `2.0 3.0 ⍸ 1.5 2.0 2.0001 2.9999 3.0 3.0001 1e100`
— dyadic `⍸` (interval form). My `where_fn` ignored the left arg and treated
the right as monadic WHERE. The right contains `1e100` (Double); Rust's
`f64::as_long()` **saturates** `1e100` to `i64::MAX` (~9.2e18), so
`vec![_; 9e18]` (scalar branch) / `for _ in 0..9e18` (rank-1 branch) requested a
runaway allocation → allocator abort (`SIGKILL`/`SIGABRT`, uncatchable by
`catch_unwind`). One abort kills the whole test binary before the summary prints.

### Fix (`kap-core/src/evaluator.rs`)
1. **Dyadic `⍸` is out-of-scope** → return a clean error when `left_val.is_some()`
   (`"dyadic ⍸ (interval form) is not implemented yet"`), so the harness counts
   it Unsupported instead of aborting. Wired in the `⍸`/`where` dispatch arm.
2. **OOM guard** (per strategy, mandated for resize/take/drop): reject when the
   element count / accumulated result exceeds `100_000_000` *before* allocating —
   in both the scalar branch (`v as usize > 100_000_000`) and the rank-1 loop
   (`(out.len()+n) > 100_000_000`). Also covers monadic `⍸ 1e100`.

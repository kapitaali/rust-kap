## [2026-08-24] P0 parser regression FIXED — nested right-arg misclassified as fn result (UNCOMMITTED)

### Symptom
`x←300 ⋄ (2+x)` → `error: unknown function: x` (oracle: `302`). Same for any
paren-grouped dyadic op with a VARIABLE right operand: `(2∧∵x)`, `(2 + y)`.
Broke every io.kap `when`-branch: `(192 ∨∵ 31 ∧∵ ¯6 ⌽∵ code)` → `unknown function: code`,
so `encodeUtf8Char` failed after `use("io.kap")` (io.kap itself loaded with 0 warnings).

### Root cause (parser.rs, finish_fn_call, ~:706 pre-edit)
The nested-right-argument branch used `Self::is_function_expr(&r)` to detect Kotlin's
FnParseResult Chain2 case (parser.kt:479–491). But `is_function_expr` returns TRUE for
every bare `Instr::Symbol` — including plain VARIABLES. Inside `(2+x)`, the nested parse
of `x` stopped at the group's close token (`at_close_now`) and was misclassified as a
function result → operator chained into atop `Train[+,x]` → eval applied variable `x`
as a function. Kotlin distinguishes by parse RESULT TYPE (Function vs Value); the port's
structural proxy over-matched. Legacy path errors differently ("No arguments specified"),
confirming both paths mishandle the shape.

### Fix (parser.rs)
1. New method `Parser::nested_right_is_fn_result(&self, r:&Instr)->bool` (~:743):
   bare `Instr::Symbol` is a function result ONLY if it names a primitive
   (`is_primitive_op(&qual)`), known fn (`is_known_fn`), or registered user fn
   (`known_functions`); all other instrs defer to `is_function_expr`.
2. Call site changed: `if at_close_now && self.nested_right_is_fn_result(&r)`.

### Verification (port vs oracle, side-by-side)
- `x←300 ⋄ (2+x)` → 302 (oracle 302) · `(2∧∵x)` → 0 (oracle 0) · `(x+2)` → 302
- `(1↑⍴) 3 4` → 2 — left-bind fork NOT regressed
- io.kap end-to-end: `namespace("io") ⋄ use("io.kap") ⋄ encodeUtf8Char @€` →
  `(226 130 172)` = oracle `⟨226 130 172⟩` EXACT

## [2026-08-24] Strings-phase — `⍎` (execute) faithful port of ParseNumberFunction

### Root cause (oracle-verified, overturned a prior assumption)
The port's `⍎` arm (evaluator.rs) did TWO non-conformant things:
1. It fell back to `eval_string` for anything that wasn't an int/rational — so
   `⍎"1+2"` returned `3` and `⍎"⍳3"` returned `1 2 3` (vector). The oracle's `⍎`
   is **`ParseNumberFunction`** (format.kt:250, engine.kt:344 `registerNativeFunction("⍎", ParseNumberFunction())`)
   — a STRICT NUMBER PARSER that throws if no number pattern matches. Probe:
   `⍎"1+2"`/`⍎"⍳3"`/`⍎"1 2 3"` → `⍎: Value cannot be parsed as a number: …` (ERROR, not eval).
2. The rational path used `i64` for the denominator, so `⍎"1/100000000000000000000000000000000000000000"`
   overflowed and fell back to `eval`, which lexed `1 / N` → "Operator without left function".

### Fix
- **`number.rs`::`parse_kap_number_string(s)` (NEW, module-level helper, ~:322):** faithful port
  of Kotlin `ParseNumberFunction.parseStringToNumber` (format.kt:267) — integer → double →
  rational, each via an ANCHORED regex using ASCII `-` (NOT Kap's `¯` high-minus), returning
  `None` when nothing matches. Reductions mirror Kotlin `makeAPLNumberWithReduction` /
  `makeAPLNumber`:
  - integer: `(-?[0-9]+)` → `Long` if it fits, else `BigInt`.
  - double: `(-?([0-9]*\.[0-9]+([eE]-?[0-9]+)?|[0-9]+[eE]-?[0-9]+|[0-9]+\.))` → `Double`.
    Three alternatives (alt-1 dot+optional-exp, alt-2 digits+exp no-dot, alt-3 `digits.`).
    A bare `.` matches none → None. (Helper `double_shape` + `exp_suffix`.)
  - rational: `(-?[0-9]+)/(-?[0-9]+)` → `BigRational`. Denom==1 collapses to int
    (long/bigint); denom==0 is KEPT as a zero-denom rational (Kotlin does not reduce it).
  - ASCII `-` only: a `¯`-prefixed string fails all three → None (matches oracle `⍎"¯10"` → ERROR).
- **`evaluator.rs` `⍎` arm rewritten** to call `KapNumber::parse_kap_number_string(t)` and emit
  Kotlin's exact error text on `None`: `⍎: Value cannot be parsed as a number: '<s>'`.
  Non-string right arg → `⍎: Argument is not a string` (aligned to oracle's
  "Argument is not a string"). The non-conformant `eval_string` fallback is GONE.

### Implementation
- **Parser** (`parser.rs::bind_operators_kotlin`, after the __KOTLIN_FALLBACK__ guard):
  `f ⍣ operand` binds when `cur` is a function expr, mirroring Kotlin parseOperator.
  Function-shaped operands (`{…}`, `⍞ref`, bare name) parse via `parse_function_atom`;
  everything else (numbers, parenthesised exprs) via `parse_primary`. Stored as
  `Instr::ValueOp { func, op_name:"⍣", operand }`.
- **Evaluator** (`evaluator.rs::apply_power_op`, ~:6470, dispatched from the ValueOp arm):
  - Dyadic application → `⍣: Function cannot be called with two arguments`.
  - Operand is `Instr::Block` (brace dfn): UNTIL loop — apply fn monadically, then
    eval_apply the block dyadically (next=left, prev=right; binds ⍺/⍵ correctly);
    stop when truthy. Guard 1e6 iterations (documented divergence: oracle loops forever).

    (apl_to_instr cannot round-trip a UserFn).
  - Operand evaluates to Number: iterate exactly N times; negative →
    `⍣: Argument to power is negative: N`.
  - Anything else → `⍣: Wanted a value of type number. Got: <detail>`.
- Two-gate rule: `⍣` added to BOTH parser recognition (bind site) and evaluator

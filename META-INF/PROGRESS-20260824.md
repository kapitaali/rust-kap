## [2026-08-24] P0 parser regression FIXED — nested right-arg misclassified as fn result (UNCOMMITTED)

### Symptom
`x←300 ⋄ (2+x)` → `error: unknown function: x` (oracle: `302`). Same for any
paren-grouped dyadic op with a VARIABLE right operand: `(2∧∵x)`, `(2 + y)`.
Broke every io.kap `when`-branch: `(192 ∨∵ 31 ∧∵ ¯6 ⌽∵ code)` → `unknown function: code`,
so `encodeUtf8Char` failed after `use("io.kap")` (io.kap itself loaded with 0 warnings).

### Root cause (parser.rs, finish_fn_call, ~:706 pre-edit)
The nested-right-argument branch used `Self::is_function_expr(&r)` to detect Kotlin's
FnParseResult Chain2 case (parser.kt:479–491). But `is_function_expr` returns TRUE for
every bare `Instr::Symbol` — including plain VARIABLES. Inside `(2+x)`, the nested parse
of `x` stopped at the group's close token (`at_close_now`) and was misclassified as a
function result → operator chained into atop `Train[+,x]` → eval applied variable `x`
as a function. Kotlin distinguishes by parse RESULT TYPE (Function vs Value); the port's
structural proxy over-matched. Legacy path errors differently ("No arguments specified"),
confirming both paths mishandle the shape.

### Fix (parser.rs)
1. New method `Parser::nested_right_is_fn_result(&self, r:&Instr)->bool` (~:743):
   bare `Instr::Symbol` is a function result ONLY if it names a primitive
   (`is_primitive_op(&qual)`), known fn (`is_known_fn`), or registered user fn
   (`known_functions`); all other instrs defer to `is_function_expr`.
2. Call site changed: `if at_close_now && self.nested_right_is_fn_result(&r)`.

### Verification (port vs oracle, side-by-side)
- `x←300 ⋄ (2+x)` → 302 (oracle 302) · `(2∧∵x)` → 0 (oracle 0) · `(x+2)` → 302
- `(1↑⍴) 3 4` → 2 — left-bind fork NOT regressed
- io.kap end-to-end: `namespace("io") ⋄ use("io.kap") ⋄ encodeUtf8Char @€` →
  `(226 130 172)` = oracle `⟨226 130 172⟩` EXACT

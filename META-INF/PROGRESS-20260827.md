## DONE today

### A. λ/function-definition tests CORRECTED (was encoding INVALID Kap)
Root cause of the failures: tests used `f ← λ(x) x × 2` — APL/Lisp contamination.
In Kap, `←` binds a **value**, `⇐` binds a **function**. `f ← {⍵×2}` is a parse error
("Right side of the arrow must be a function"). The skill was already correct
(`syntax-core.md:226` defines `⇐`; line 187/250 state `λ(params)` is NOT Kap).

Fixes (Real-Kap-verified against JVM oracle):
- `evaluator.rs::eval_lambda_apply`: `f ⇐ {⍵×2} ⋄ f 5` → `10`; `g ⇐ {⍺+⍵} ⋄ 3 g 4` → `7`;
  assert `λ(x) x × 2` is **rejected** (port → `error: undefined symbol: x`).
- `evaluator.rs::eval_parenthesised_groups`: `(f 5)+1` → `11`; `f (3+4)` → `14`
  (with `f ⇐ {⍵×2}`).
- `session.rs::session_persists_lambda_and_sees_globals`: `double ⇐ {⍵×2}` → `42`;
  `addk ⇐ {⍵+k}` (with `k ← 3`) → `13`.
- Added `eval_fails(src) -> bool` test helper: the rejection assertion must tolerate
  an expected parse/eval Err (the shared `eval()` helper does `.expect("eval failed")`
  and would otherwise panic on `λ(x)…`). Without this helper the test panicked, not failed.
- Parser `λ` is reference-only (`λfoo` / `λ(…)` / `λ{…}`) and CORRECT — do NOT add `λ(params)`.

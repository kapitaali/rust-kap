## Work landed this session

### 1. `6395485` — two independent correctness fixes

**(a) Left-bind whose bound VALUE is an expression, not a literal.**
`((-2)↑) ⍳6`, `((1+1)↑) ⍳6`, `((-2)+) 5` all failed with `only symbol/lambda
functions supported yet`, while `(¯2↑) ⍳6` worked — high-minus LITERAL fine,
parenthesised negation EXPRESSION not. That asymmetry was the diagnostic tell.

Traced, not guessed: the parser already built the correct `Train[Apply{-,2}, ↑]`.
The defect was `is_value` in `kap-core/src/evaluator.rs`, which accepted only
`Literal | Array | Empty`, so `apply_train`'s left-bind arm
(`funcs.len()==2 && is_value(&funcs[0])`) never matched, execution fell through to
the ATOP case, and the value member was then treated as a function. Kotlin's
`makeLeftBindFunction` (parser.kt:486) binds the whole accumulated `leftArgs` list —
any value instruction. Widened to `Apply|Index|BooleanOp|Value`; `Symbol` is
deliberately EXCLUDED (a bare symbol in a train is normally a function reference, so
admitting it breaks plain 2-trains `(f g)`) — which is why `(n↑)` with a variable is
still open, see PROBLEM.md OPEN-B.

**(b) `⌊`/`⌈` must reduce an exact-integer rational — found BY the new curated row.**
Adding `("((⌈3÷2)↑) ⍳6", "(0 1)")` turned the gate RED with `↑/↓ counts must be
integers`. Probing showed `typeof ⌈3÷2` → port `kap:rational` vs oracle
`kap:integer`. Kotlin calls `makeAPLNumberWithReduction()` in the rational branch of
both `⌊` (math_functions.kt:1278) and `⌈` (:1341). Added
`KapNumber::reduce_rational` in `kap-core/src/number.rs` (denominator 1 ⇒ `Long`, or
`BigInt` when it does not fit) and applied it in `ceil()` and `floor()`.
Rationals that must stay rational verified untouched: `typeof 3r2` → `kap:rational`,
`3÷2` → `3/2`. Negatives exact: `⌊¯3r2` → `¯2`, `⌈¯3r2` → `¯1`.

**Process cost, recorded honestly:** three speculative parser edits were made and
ALL REVERTED (`next_is_paren_operator` nested-group handling, `fold_train_members`
value set, `parse_paren_vfn_chain`'s `first_is_value`). A temporary `KAP_TRACE_PAREN`
probe **never fired**, which disproved the assumed code path and redirected the hunt
to the evaluator. Detail: `PROGRESS-20260826i.md`.

### 2. `cd2b6bf` — paren-group value as a left-bind in ANY position

**Tell:** `((-2)↑)` worked standalone AND as a fork's LEFT tine, but failed as its
RIGHT tine, with the error column on the INNER group's `)`; `((1+1)↑)` worked
everywhere. Position-dependent + function-glyph-initial vs number-initial.

**Traced** with a `KAP_TRACE_FA` probe printing the branch taken and the built instr:

```
⌽«,»((-2)↑)   → vfn_chain OK Array { elements: [Symbol{-}, Literal(2)] }   ← STRANDED
⌽«,»((1+1)↑)  → vfn_chain OK Train  { funcs: [Apply{+,1,1}, Symbol{↑}] }   ← correct
```

`Array[Symbol{-}, Literal(2)]` was the whole diagnosis — the inner `(-2)` was
stranded, not applied, and a strand ending in an unbound primitive trips the
`Instr::Array` guard in `evaluator.rs:720` → `No arguments specified for function`.

Two layers, both `kap-core/src/parser.rs`:
1. `parse_paren_vfn_chain`'s `first_is_value` guard (~:2957) listed
   Number/Char/Str/SymbolValue/OpenBracket/QuotePrefix but **not `OpenParen`**, so a
   paren-leading group was routed to `try_parse_train` (function members only), which
   cannot represent `(-2)` — a value expression whose first token is a function glyph.
2. `parse_paren_accum`'s catch-all then handled the nested `(` via
   `parse_function_atom`, re-entering that same fn-only path and producing the strand.

Kotlin has no such split: the inner `parseExpr` (parser.kt:939) recurses on `(` and
returns EITHER a value or a function holder.

**Fix:** added `Some(Token::OpenParen) => true` to `first_is_value`, plus an explicit
`OpenParen` arm in `parse_paren_accum` that parses the group as a **self-contained
balanced unit** (`parse_function_atom`) and classifies the result with
`is_function_expr` — function ⇒ same continuation as the symbol-function arm
(Empty ⇒ left-bind, Fn ⇒ Chain2/atop, Value ⇒ Apply, each with leading-value
variants); anything else ⇒ re-parse with `parse_primary` and strand.

**Failed first attempt, recorded:** the first version recursed straight into
`parse_paren_accum` after consuming `(`. WRONG — that accumulator returns at the
FIRST `)` it meets, so parsing `-`'s argument ate the paren closing the inner group
and merely relocated the parse error. Detail: `PROGRESS-20260826j.md`.

## Skill updates made this session (`rust-kap-dev`)

Four durable lessons added:
- **Trace the instr before editing** when the symptom is wrong/absent behaviour;
  a probe that does not fire IS the finding (it disproves the code path).
- **Position-dependent failure ⇒ suspect the DISPATCH GUARD**, not the parse of the
  construct — diff the ROUTES (grep the guard lists) before reading either function.
- **`parse_paren_accum` returns at the first `)`** — never handle a nested `(` by
  recursing straight into it; parse a balanced unit and classify.
- **Verify binary freshness by TIMESTAMP, not cargo's word.** `touch <one file>` was
  repeatedly insufficient; cargo printed "Finished in 0.04s" (no relink) and probes
  showed pre-edit behaviour. Use `touch kap-core/src/*.rs && cargo build -p kap-cli`
  and confirm with `ls -l --time-style=+%H:%M:%S target/debug/kap` (real relink ≈9s).
- **Composed curated rows beat single-feature rows** — bug (b) above was found only
  because a row exercised left-bind AND `⌈` together.

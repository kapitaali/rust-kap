## [2026-08-21] Fixed `f[axis]` (dyadic scalar axis-specifier) — CORRECTED a wrong error claim

The user caught a real bug: I had claimed `2 +[0] 3` correctly errors "A or B has to be
rank 1", but Real Kap (shell + browser JS client) returns **`5`**. Investigated against
the Kotlin source and the oracle — my claim was **wrong**.

**Root cause of my wrong claim:** I trusted the Rust port's own `num2_axis` guard (which
hard-required the LEFT operand to be a rank-1 vector and rejected a scalar) instead of
reading Kotlin. Kotlin `MathCombineAPLFunction.eval2Arg` (math_functions.kt:501-503)
short-circuits **BEFORE** any axis logic:
```kotlin
if (a0 is APLSingleValue && b0 is APLSingleValue) return combine2Arg(a0, b0)
```
So two scalars IGNORE the axis entirely and just combine → `2 +[0] 3` = `5` (also `2 +[1] 3`
= `5`). The "A or B has to be rank 1" error only fires when at least one arg is non-scalar
and neither is rank 1 (e.g. `2 +[0] 3 4 5` → "Axis 0 is not valid. Expected: 0").

**Two fixes:**
1. `evaluator.rs` (`Instr::AxisApplied` dispatch): before routing to `num2_axis`, if BOTH
   `left_v` and `right_v` are scalar `Number`s, apply the plain `apply_op` and return —
   mirroring the Kotlin scalar+scalar short-circuit. (Also updates the stale doc comment on
   `num2_axis`.)
2. `parser.rs`: the dyadic **strand** loop never parsed `f[axis]` — a stranded left operand
   (`1 2 3 +[0] 4 5 6`) greedily consumed `[0] …` as bracket-index on the right arg, giving
   the bogus "arrays of different length (3 vs 4)". Added an axis-specifier parse in the
   dyadic loop, **gated to scalar-arithmetic operators (`+ - × ÷ *`)** — the only functions
   `num2_axis` supports — so `,` (catenate) does NOT swallow a following `[` (the port
   treats `[3;4]` as a list literal; `eval_catenate` asserts that leniency). The same gate
   was retro-applied to the single-value `L f R` axis-peek.

**Verified byte-for-byte vs oracle:** `2 +[0] 3 → 5`, `2 +[1] 3 → 5`, `1 2 3 +[0] 4 5 6 →
(5 7 9)` (oracle `⟨5 7 9⟩`), `10 20 30 40 +[0] 4 3 2 ⍴ 100+⍳24 → (110…163)` (oracle boxed
`┌┌→──┐`, shape `(4 3 2)` confirmed via `⍴`). Error cases still error: `2 +[0] 3 4 5`,
`1 2 3 +[0] 2 2⍴…`, `4 3 2⍴… +[0] 10 20 30 40`.

**Gates green:** lib 92/0, curated 1/0. Added 4 curated `f[axis]` parity rows.

## [2026-08-21] Tier A of stdlib-kernel: `use()` + `⫇` + `,[axis]` — **COMPLETE** (feature/wheres-extra)

This is the ROADMAP stage after the `f[axis]` work — wire the stdlib-kernel so
`base-functions.kap` can load and unblock `⎕A`/`⎕p`/`⎕a`/`⎕d`. **All four sub-targets done
and verified vs the oracle.**

### A. `⫇` / `group` (GroupFunction, group-index.kt)
- Registered in BOTH `is_primitive_name` AND `is_primitive_op` (`⫇` / `group`) — two-registration rule.
- New dispatch arm in `eval_apply` → new `Engine::group_indices` method, faithful to Kotlin
  `GroupFunction.eval2Arg`:
  - Left `L` = rank-1 vector of group indices; negative index ⇒ element skipped.
  - Right `R`: major axis split into cells (scalar cells if R is rank-1, else rank-1
    sub-arrays along the major axis).
  - Result = vector of `APLValue`s, one per distinct non-negative index; gaps filled with
    `APLValue::Null` (so `1 2 3 4 ⫇ 1 1 2 2` → `(⟨1 2⟩ ⟨3 4⟩ ⍬)` in oracle `(…)` form;
    port renders nested-array form but values+shape identical).
- Verified byte-for-byte vs oracle on all 3 cases (only `()` vs `⟨⟩` glyph differs).

### B. `,[axis]` laminate (concatenate-array.kt `joinByAxis`/`joinByLaminate`)
- Extended the axis-detection gate (was `+ - × ÷ *` only) to also include `,` / `⍪` in BOTH
  the single-value `L f R` axis-peek AND the dyadic strand loop in `parser.rs`. Now
  `1 2 3 ,[0.5] 1 2 3` parses `,[0.5]` as an axis specifier (not a list literal).
- `AxisApplied` handler now passes the **full fractional `KapNumber` axis** into a new
  `Engine::catenate_axis` method (instead of only the integer `as_long`). `catenate_axis`
  mirrors Kotlin `computeLaminateAxis`/`joinByAxis`/`joinByLaminate`:
  - axis is integer (or within 0.01 of one) ⇒ integer-axis concat (`join_by_axis`).
  - axis fractional ⇒ laminate at `ceil(d)` (insert length-1 axis at that position, then concat).
- **Behavioral correction (conformance fix):** Real Kap treats `,[…]` after `,` as **always**
  an axis. The port previously let `[3;4]` after `,` be a list literal, and `eval_catenate`
  asserted `([1;2] , [3;4]) → (1 2 3 4)`. Oracle: `1 2 3 ,[3;4] 5 6` is a **type error**
  ("Wanted a value of type number", `[3;4]` is a 2-element list, not a number). So I
  - added `,`/`⍪` to the axis gate, and
  - **updated `eval_catenate`**: it now asserts `([1;2] , [3;4])` ERRORS (matching Real Kap).
- Verified byte-for-byte vs oracle: `1 2 3 ,[0.5] 4 5 6 → (1 4 2 5 3 6)` shape `(3 2)`;
  `1 2 3 ,[0.5] 1 2 3 → (1 1 2 2 3 3)` `(3 2)`; `(2 2) ,[0.5] (2 2) → (2 2 2)` `(2 2 2)`;
  `⍴ 1 2 3 ,[0.5] 1 2 3 → (3 2)`.

### C. `use("file.kap")` (LoadFileFunction / resolveLibraryFile)
- Registered `use` in BOTH `is_primitive_name` AND `is_primitive_op`.
- New dispatch arm `self.use_file(&name, env)` → new `Engine::use_file` method.
- Mirrors Kotlin `LoadFileFunction`/`resolveLibraryFile`: argument is a **filename**, resolved
  by **basename** across a search path:
  1. configured `--lib-path` dirs (see F2),
  2. current working directory,
  3. `$KAP_LIB` env var,
  4. repo `kap-stdlib/std` (computed from `CARGO_MANIFEST_DIR` parent → `kap-stdlib/std`).
- **Recursion guard (deliberate, documented divergence):** Real Kap `use("self.kap")` that
  self-references **StackOverflows** (verified against the oracle — a minimal
  `use("self.kap")` test crashed the JVM). `base-functions.kap` begins with
  `use("base-functions.kap")` and would infinitely recurse. So `Engine` gained an
  `include_stack: Rc<RefCell<HashSet<String>>>`; `use_file` skips a basename already in the
  stack and uses an `IncludeGuard` RAII drop to pop it. This is the only way to make
  `base-functions.kap` usable — flagged as a port divergence from Real Kap's crash.
- Evaluates the file in the **current** env (so its top-level `∇`/`⇐` definitions land where
  the `use` call appears).

### D. `--lib-path` / `-p` flag (the user-required standard-library location)
Wired a first-class stdlib location, matching kap-jvm-text's `--lib-path`/`--load`:
- `lib.rs`: `Engine` gained `lib_paths: Rc<RefCell<Vec<PathBuf>>>`; new `Engine::set_lib_paths(&[S])`.
- `evaluator.rs::use_file`: search path begins with `self.lib_paths` (configured `--lib-path`
  dirs) **first**, then CWD, `$KAP_LIB`, then repo `kap-stdlib/std` — so `--lib-path` takes
  precedence exactly like the oracle.
- `session.rs`: `Session::set_lib_paths` forwarder.
- `kap-cli/src/main.rs`: parses `--lib-path=PATH`, `--lib-path PATH`, `-p PATH`, `-pPATH`;
  applies to the session before eval/file/REPL.

Oracle reference: `kap-jvm-text --lib-path=~/Apps/array/kap-jvm-text/standard-lib` then
`⊢ ⎕A` → `⊢ "ABCDEFGHIJKLMNOPQRSTUVWXYZ"` (matches default). The port's flag resolves
`base-functions.kap` via it (verified: no "library file not found").

### E. Four fixes that made `⎕A`/`⎕a`/`⎕d` reachable (the load was previously aborting)
All grounded in the oracle, not guessed:

**E1. Lexer: `⎕` starts a multi-char symbol.** `⎕A`, `⎕p`, `⎕pl`, `⎕a`, `⎕d` are single
Kap symbols. The lexer used to emit `⎕` as a one-char glyph token then `A` separately.
Fixes (`lexer.rs` / `lex_helpers.rs`): `is_symbol_start` now true for `⎕`; `lex_symbol`
consumes `⎕` + following alphanumerics into one run; the non-ASCII single-glyph branch now
skips `⎕` so it falls through to the symbol-start path.

**E2. `declare` tolerates a symbol group AND an operator operand.** `base-functions.kap`
lines 8/17/18 call `declare(:export ⌸)`, `declare(:export (⎕p ⎕pl ⎕A ⎕a ⎕d))`,
`declare(:const (⎕A ⎕a ⎕d))`. The `declare` arm (`evaluator.rs`) now: if 2nd element is
`Symbol` → export it; if `Array` → export each `Symbol` member (group form); otherwise
(e.g. an operator operand like `⌸`, deferred) → skip gracefully (Ok).

**E3. Parenthesised bare-symbol groups are list literals, not trains.** `try_parse_train`
(`parser.rs`) used `is_function_expr` (which admits ANY symbol) as the "all members are
functions" test, so `(⎕p ⎕pl ⎕A ⎕a ⎕d)` became a **5-train** and the evaluator rejected it
("monadic trains of length 5"). Fixes:
- Changed the train-membership test to `is_definite_function` (primitives / known fns /
  lambdas / derived / trains — NOT bare unknown symbols). A group of bare symbols is now
  correctly NOT a train.
- Added a fall-through branch: if every member is a plain `Instr::Symbol`, return
  `Instr::Array { elements: funcs }` — a vector-of-symbols list literal, which is exactly what
  `declare`'s argument is in Kotlin.

**E4. `⇐` with a parenthesised TRAIN RHS** (`⎕p ⇐ (⊣ io:print)`, `⎕pl ⇐ (⊣ io:println)`,
`base-functions.kap` lines 10–11). `is_definite_function` previously only accepted a 2-train
when both members were primitive/known functions. `io:print` lexes as
`Symbol { name:"print", namespace:Some("io") }` — a *module-qualified* name, which is never a
local variable, so it must count as a definite function. Fix: `is_definite_function` now also
returns true when `namespace.is_some()`. `(⊣ io:print)` now parses as a valid atop (2-train).

> Note: `⎕p`/`⎕pl` are *functions* (not constants) — at runtime they apply `io:print`/
> `io:println`, which the port does not implement (no `io` module). For Tier A the goal is
> *loading the file and reading the constants* `⎕A`/`⎕a`/`⎕d`, which now works.

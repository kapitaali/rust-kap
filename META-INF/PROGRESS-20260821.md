## [2026-08-21] Bracket indexing `x[sel]` → `index_select` (feature/wheres-extra)

Completed and verified the bracket-index selection path that was in-progress at
session rollover. `Instr::Index` (the `[i][j]` suffix built by `parser.rs`) now
routes to a new `Engine::index_select` instead of the old `pick` call.

`index_select` mirrors Kotlin `APLValue.get` / `indexFromPositionNegativeSupport`
(`dimension.kt`):
- Per-`;`-axis section: `⍬`/empty → whole axis; scalar index → **collapse** that
  axis (rank-0 scalar result, Kap discloses the element, not a length-1 array);
  vector index → that many cells along the axis.
- Negative indices wrap (`¯1` = last) via `check_and_adjust_selected_index`.
- Result whose every section was scalar → rank-0 scalar (`m[1;2]` → `5`, not `(5)`).
- Chained `x[i][j]` works by re-indexing the inner result.

- `cargo test -p kap-core --lib` → **92 passed; 0 failed**
- `cargo test -p kap-core --test conformance curated_kap_parity` → **1 passed; 0 failed**

`⟨⟩` glyph differs on multi-element rows): every N-D case matched byte-for-byte,
including error text ("Index list length must be less than or equal to the rank of
the argument") and Kap's deliberate `1 2 3 4[2]` error.

## [2026-08-21] `≬` / `toList` (+ `fromList`) implemented (feature/wheres-extra)

Scoped the next Phase-6 open target. Discovered the roadmap's `∘`/`≬` grouping was
a MISLABEL: `∘`/`⍛` (compose / reverse-compose trains) were already fully wired
(lexer→parser→ast→evaluator) and pass the oracle. `≬` is **not** compose — Kotlin
source (`div_functions.kt` `ToListFunction`) shows it is the `toList` primitive:
monadic-only, boxes a scalar or 1-D array into a rank-0 list (oracle `⟨⟩` type),
ALWAYS boxes even a primitive scalar (`≬5 → (5)` not `5`), rank>1 errors, dyadic
errors. `fromList` is its inverse.

Implementation (faithful value-semantics; port has no separate list type so it
models the box as a rank-0 `Nested([v])` → displays `((...))`, the known DISPLAY
glyph divergence, not a value defect):
- `evaluator.rs`: new `to_list` / `from_list` helpers + dispatch arms for
  `"≬" | "toList"` (monadic-only) and `"fromList"` in the `apply_builtin` match.
- Registered in BOTH `evaluator.rs::is_primitive_name` AND `parser.rs::is_primitive_op`
  (`≬` / `toList` / `fromList`) — the two-registration rule.
- `conformance.rs`: 3 curated parity rows (value-only; error-text rows verified by
  hand and noted in comments, since the harness can't assert error messages).

## [2026-08-21] `⍕` monadic format flatten fix + format-family audit (feature/wheres-extra)

Audited the remaining open Phase-6 targets. Findings:

- **`⌸`/`⌺` are NOT native Kotlin builtins** — they resolve through the `use()`-loaded
  stdlib (`kap:keys`/`kap:stencil` in `base-functions.kap`). Confirmed by reading
  `engine.kt`: `⌸`/`⌺` appear only in the *lexer symbol set*, not as registered native
  functions (only `keys`/`map` is native). Out of reach until the deferred stdlib-kernel
  is built. Not scoping this.
- **`⍋⍒`-with-axis is N/A** — Kotlin `GradeFunction` extends `NoAxisAPLFunction`, so axis
  specifiers are explicitly unsupported (oracle errors "Function does not support axis
  specifier"). Nothing to implement.
- **Format family**: the dyadic `$s`/`$h`/`$$` directive compiler (Kotlin `format.kt`)
  was ALREADY implemented and matches the oracle. But **monadic `⍕` was wrong**: it used
  `format_value` (wraps arrays in `( … )` with spaces), so `⍕ 1 2 3 → "(1 2 3)"`
  instead of the oracle's `"123"`.

Fix (faithful to Kotlin `formatted(FormatStyle.PLAIN)`):
- `lib.rs`: new `APLValue::format_plain` — recursively flattens to scalar leaves and
  concatenates with NO separators/parentheses (strings contribute chars unquoted).
- `evaluator.rs`: monadic `⍕` arm now calls `format_plain` instead of `format_value`.
  Dyadic directive path unchanged (already correct).

Verified port-vs-oracle byte-for-byte: `⍕ 1 2 3 → "123"`, `⍕ 10 20 30 → "102030"`,
`⍕ (2 2⍴⍳4) → "0123"`, `⍕ ⊂1 2 3 → "123"`, `⍕ ⊂5 → "5"`, `⍕ 1.5 2.5 → "1.52.5"`,
`⍕ "ab" "cd" → "abcd"`, `⍕ ⍬ → ""`. Dyadic regression-free: `$5s⍕42 → "   42"`,
`$h⍕"<b>" → "x=&lt;b&gt;"`, `"$s and $s"⍕(1 2) → "1 and 2"`.

Gates (both green after `cargo build -p kap-cli`):

## [2026-08-21] Implement `⍉` partial-axis (natural target from pulled corpus) (feature/wheres-extra)

Picked the **`⍉` axis** gap surfaced by Elias's 2026-08-21 pull (the new
`TransposeTest__mismatchingAxisCount*` / `__multiDimensionTransposeWith*LeftArg*` cases).
The port already supported full axis permutations; the strict `axes.len() == rank` check
was wrong vs Kotlin's *prefix-fill* rule.

**Fix** (`evaluator.rs::transpose`): when the left arg is shorter than the rank, the
remaining axes are appended in ascending order (skipping those used). `0 1 ⍉ 3 4 5⍴⍳60`
→ perm [0,1,2] (identity) → dims `⟨3 4 5⟩`. A left arg longer than rank still errors.
Grounded in Kotlin `TransposeFunction.eval2Arg` (transpose.kt:495-514).

`0 1 ⍉ 3 4 5⍴⍳60`→`(3 4 5)`, `1 2 0 ⍉ 2 3 4⍴⍳24`→`(4 2 3)`, `0 1 ⍉ 2 3 4⍴⍳24`→`(2 3 4)`,
`2 1 0 ⍉ 3 4 5⍴⍳60`→`(5 4 3)` (full perm unchanged). Element values also match.

**Gates green:** lib 92/0, curated 1/0. Added 4 curated `⍉` partial-axis rows.

## [2026-08-21] Fixed `f[axis]` (dyadic scalar axis-specifier) — CORRECTED a wrong error claim

The user caught a real bug: I had claimed `2 +[0] 3` correctly errors "A or B has to be
rank 1", but Real Kap (shell + browser JS client) returns **`5`**. Investigated against
the Kotlin source and the oracle — my claim was **wrong**.

**Root cause of my wrong claim:** I trusted the Rust port's own `num2_axis` guard (which
hard-required the LEFT operand to be a rank-1 vector and rejected a scalar) instead of
reading Kotlin. Kotlin `MathCombineAPLFunction.eval2Arg` (math_functions.kt:501-503)
short-circuits **BEFORE** any axis logic:
```kotlin
if (a0 is APLSingleValue && b0 is APLSingleValue) return combine2Arg(a0, b0)
```
So two scalars IGNORE the axis entirely and just combine → `2 +[0] 3` = `5` (also `2 +[1] 3`
= `5`). The "A or B has to be rank 1" error only fires when at least one arg is non-scalar
and neither is rank 1 (e.g. `2 +[0] 3 4 5` → "Axis 0 is not valid. Expected: 0").

**Two fixes:**
1. `evaluator.rs` (`Instr::AxisApplied` dispatch): before routing to `num2_axis`, if BOTH
   `left_v` and `right_v` are scalar `Number`s, apply the plain `apply_op` and return —
   mirroring the Kotlin scalar+scalar short-circuit. (Also updates the stale doc comment on
   `num2_axis`.)
2. `parser.rs`: the dyadic **strand** loop never parsed `f[axis]` — a stranded left operand
   (`1 2 3 +[0] 4 5 6`) greedily consumed `[0] …` as bracket-index on the right arg, giving
   the bogus "arrays of different length (3 vs 4)". Added an axis-specifier parse in the
   dyadic loop, **gated to scalar-arithmetic operators (`+ - × ÷ *`)** — the only functions
   `num2_axis` supports — so `,` (catenate) does NOT swallow a following `[` (the port
   treats `[3;4]` as a list literal; `eval_catenate` asserts that leniency). The same gate
   was retro-applied to the single-value `L f R` axis-peek.

**Verified byte-for-byte vs oracle:** `2 +[0] 3 → 5`, `2 +[1] 3 → 5`, `1 2 3 +[0] 4 5 6 →
(5 7 9)` (oracle `⟨5 7 9⟩`), `10 20 30 40 +[0] 4 3 2 ⍴ 100+⍳24 → (110…163)` (oracle boxed
`┌┌→──┐`, shape `(4 3 2)` confirmed via `⍴`). Error cases still error: `2 +[0] 3 4 5`,
`1 2 3 +[0] 2 2⍴…`, `4 3 2⍴… +[0] 10 20 30 40`.

**Gates green:** lib 92/0, curated 1/0. Added 4 curated `f[axis]` parity rows.

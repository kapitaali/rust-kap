## [2026-08-21] Bracket indexing `x[sel]` → `index_select` (feature/wheres-extra)

Completed and verified the bracket-index selection path that was in-progress at
session rollover. `Instr::Index` (the `[i][j]` suffix built by `parser.rs`) now
routes to a new `Engine::index_select` instead of the old `pick` call.

`index_select` mirrors Kotlin `APLValue.get` / `indexFromPositionNegativeSupport`
(`dimension.kt`):
- Per-`;`-axis section: `⍬`/empty → whole axis; scalar index → **collapse** that
  axis (rank-0 scalar result, Kap discloses the element, not a length-1 array);
  vector index → that many cells along the axis.
- Negative indices wrap (`¯1` = last) via `check_and_adjust_selected_index`.
- Result whose every section was scalar → rank-0 scalar (`m[1;2]` → `5`, not `(5)`).
- Chained `x[i][j]` works by re-indexing the inner result.

Gates (all green):
- `cargo test -p kap-core --lib` → **92 passed; 0 failed**
- `cargo test -p kap-core --test conformance curated_kap_parity` → **1 passed; 0 failed**
- `cargo build -p kap-cli` → clean (pre-existing dead-code warnings only)

Verified port-vs-oracle by side-by-side REPL probe (value matches; only `()` vs
`⟨⟩` glyph differs on multi-element rows): every N-D case matched byte-for-byte,
including error text ("Index list length must be less than or equal to the rank of
the argument") and Kap's deliberate `1 2 3 4[2]` error.

**One flagged divergence (pre-existing, NOT an index_select bug):** a
vector-of-vectors `((1 2 3)(4 5 6)(7 8 9))` is generalized by the port into a true
2-D `(3 3)` array, whereas Real Kap keeps it rank-1 `(3)`. So the port's chained
`…[0][2]` → `3` while the oracle errors (rank-1 has no 2nd axis). The algorithm is
correct for genuine N-D arrays; this is the same nested-vector generalization gap
already tracked under DISPLAY/DEFERRED. No change made — recorded for later.

## [2026-08-21] `≬` / `toList` (+ `fromList`) implemented (feature/wheres-extra)

Scoped the next Phase-6 open target. Discovered the roadmap's `∘`/`≬` grouping was
a MISLABEL: `∘`/`⍛` (compose / reverse-compose trains) were already fully wired
(lexer→parser→ast→evaluator) and pass the oracle. `≬` is **not** compose — Kotlin
source (`div_functions.kt` `ToListFunction`) shows it is the `toList` primitive:
monadic-only, boxes a scalar or 1-D array into a rank-0 list (oracle `⟨⟩` type),
ALWAYS boxes even a primitive scalar (`≬5 → (5)` not `5`), rank>1 errors, dyadic
errors. `fromList` is its inverse.

Implementation (faithful value-semantics; port has no separate list type so it
models the box as a rank-0 `Nested([v])` → displays `((...))`, the known DISPLAY
glyph divergence, not a value defect):
- `evaluator.rs`: new `to_list` / `from_list` helpers + dispatch arms for
  `"≬" | "toList"` (monadic-only) and `"fromList"` in the `apply_builtin` match.
- Registered in BOTH `evaluator.rs::is_primitive_name` AND `parser.rs::is_primitive_op`
  (`≬` / `toList` / `fromList`) — the two-registration rule.
- `conformance.rs`: 3 curated parity rows (value-only; error-text rows verified by
  hand and noted in comments, since the harness can't assert error messages).

Gates (all green after `cargo build -p kap-cli` — stale-binary trap avoided):
- `cargo test -p kap-core --lib` → **92 passed; 0 failed**
- `cargo test -p kap-core --test conformance curated_kap_parity` → **1 passed; 0 failed**

Verified port-vs-oracle by side-by-side probe: `≬ 1 2 3 → ((1 2 3))` (oracle
`⟨1 2 3⟩`), `≬ 5 → (5)`, `≬ "abc" → ("abc")`, `≬ 2 2⍴⍳4` and `3 ≬ 5` error text
byte-for-byte; `fromList ≬ 1 2 3 → (1 2 3)` (oracle `⟨1 2 3⟩`).

Docs: `ROADMAP.md` (`∘`/`⍛`/`≬` marked DONE, mislabel corrected, `≬` added to
"Already closed"), `KNOWN-NONCONFORMANCE.md` (new `≬`/`toList` section; stale
"`∘`/`≬` unimplemented" DEFERRED line fixed).

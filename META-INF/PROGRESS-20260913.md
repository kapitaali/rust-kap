## Fix 1 — dyadic `defer` (`simpleLazyEvaluation2Arg`, +1 OK)

**Symptom:** `((100 foo defer 10) (100 foo defer 20) (100 foo defer 30))[2]`
with dyadic `∇ (a) foo (b)` died with
`parse error: Index dereference without argument` at the `[2]`.
Oracle: `30135` (prints `30`, result `135`).

**Root cause:** Kotlin `processFn` (parser.kt:432) calls `parseOperator(fn)`
FIRST — `defer` binds to `foo` as a pure operator (no value operand), and the
`10` is parsed AFTER as the call's right arg
(`FunctionCall2Arg(derived, 100, 10)`). The port's `bind_operators_kotlin`
`defer` arm instead consumes `defer v` eagerly into
`ValueOp{func, defer, operand}`, so `finish_fn_call(foo, left=[100])` saw no
right arg and built a left-bind `Train[100, ValueOp]`; the stranded Trains
then left `[2]` to be misread as a right arg.

**Fix** (`kap-core/src/parser.rs`, `finish_fn_call` `!has_right` branch): a
`defer`-ValueOp with non-empty left builds
`Apply{fn: ValueOp{foo,defer,10}, left: bound, right: Empty}` instead of a
left-bind Train. The dummy `Empty` right is never evaluated — the evaluator's
`defer` arm (evaluator.rs:3371) builds `Apply{func, left, operand}` from the
ValueOp parts and ignores apply-time `right` (verified: no forcing of
left/right precedes the ValueOp dispatch at evaluator.rs:3325).

Monadic path untouched (`left_args.is_empty()` returns the ValueOp as-is;
yesterday's `d7d06fe` stranding still applies).

**Oracle transcripts** (kap-jvm-text `--no-standard-lib --no-lineeditor`,
single-line `⋄`-joined; multi-line stdin misparses — known REPL artifact):
- `∇ (a) foo (b) { io:print b ⋄ a + b + 5 } ⋄ ((100 foo defer 10) (100 foo defer 20) (100 foo defer 30))[2]`

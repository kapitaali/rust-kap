## T2.2 status: PARTIAL — targeted fix, full issue NOT closed

The ROADMAP Appendix A.3 framing "T2.2 — Reduce `⊥` user-body OOB
panic (56 cases)" was an overstatement. The real failure modes in
the Kotlin `EncodeTest.kt` corpus (31 cases, derived from the
kotlin_tests.jsonl rows 139-167) are:

1. **`Null` (⍬) treated as rank 0 instead of rank 1 size-0.** The
   port's `APLValue::Null` is a unit variant (no inner array, no
   dimensions), whereas Kotlin's `APLEmptyArray` has
   `dimensions = [0]` (rank 1, size 0) — see
   `array/src/commonMain/kotlin/.../types.kt:1660` and
   `dimension.kt:234` (`EMPTY_LIST_DIMENSIONS = Dimensions(intArrayOf(0))`).
   This affects every builtin that dispatches on `b.rank()` or
   `b.dimensions()`, not just `⊥`/`⊤`. Concrete disagreements
   (oracle ↔ port):
   - `⍴⍬` → `0` (Kotlin) vs `()` (port)
   - `9 ⊥ ⍬` → `0` (Kotlin) vs ERROR "⊥ digits must be a number" (port)
   - `×⍬` → `0` (Kotlin) vs ERROR "× requires a number" (port)
   - `⊂⍬` → `┌─┐` (Kotlin) vs `⍬` (port)
   - `+⌿⍬` → `0` (Kotlin) vs `⍬` (port)
   - `0⍴⍬` → `⍬` (Kotlin) vs `()` (port)
   - `⍬⍴⊂1 2 3` → `┌───────┐` (Kotlin) vs `(1 2 3)` (port)

2. **Integer-only arithmetic in encode/decode.** The port's
   `fn decode` (which implements `⊥`) reads every digit via
   `n.as_long().ok()`, silently truncating doubles. Kotlin promotes
   to `Double` whenever any operand is a double (verified by
   `EncodeTest.kt:38-42 floatingPointArguments`:
   `10 ⊥ 2 3.1 3.1 → 234.1`). The port returned `233`.

## What this session changed (targeted)

**File:** `kap-core/src/evaluator.rs` (uncommitted, in working tree)

### Fix 1: Null normalization at the entry of `fn decode` (⊥)

Wraps `Null` into a `KapArray` of shape `[0]` before any
rank/dimension check. This is a function-local fix and follows the
same `arrayify()` pattern Kotlin uses in `reshape.kt:249-271`. It
does NOT make `⍬` behave like a rank-1 size-0 array outside of
`fn decode` — the other builtins (`×`, `+`, `⊂`, `⍴`, `+⌿`, etc.)
still see `Null` as rank 0.

```rust
// Null (⍬) is a rank-1 size-0 array per Kotlin `APLEmptyArray`. The port's
// `APLValue::Null` is unit-shaped (rank 0), so we materialize an empty
// rank-1 array here for the rest of the function.
let b = if let APLValue::Null = b.as_ref() {
    Rc::new(APLValue::Array(Rc::new(KapArray::new(
        vec![0],
        ArrayData::Nested(vec![]),
    ))))
} else { b };
```

### Fix 2: Double auto-promotion in `fn decode` (⊥)

Adds a `use_double` boolean at the top, computed by scanning A and
B for any `KapNumber::Double(_)`. The weight-building and
digit-accumulation loops branch on this flag: i64 path is unchanged
for the all-integer case; the f64 path is new. Both paths emit the
same `KapNumber` types they would have before, with the only
difference being the inner arithmetic precision.

```rust
let use_double = {
    let a_is_double = a.elements().iter().any(|e| matches!(
        e.as_ref(), APLValue::Number(n) if matches!(n, KapNumber::Double(_))
    ));
    let b_is_double = b.elements().iter().any(|e| matches!(
        e.as_ref(), APLValue::Number(n) if matches!(n, KapNumber::Double(_))
    ));
    a_is_double || b_is_double
};
```

## What was NOT changed (out of scope for this turn)

The full `Null` divergence requires a port-wide rework. The current
`APLValue::Null` is a unit variant with no place to attach a
`KapArray` of shape `[0]`. Fixing it properly means one of:

- **(A) Add a `KapArray` inside `Null`:** change the variant to
  `Null(AplRef<KapArray>)` where the array has dimensions `[0]`.
  Then update every `match` arm that pattern-matches on
  `APLValue::Null` (~50 sites in `evaluator.rs` alone, per the
  search counts at the start of this session). This is invasive
  but is the "correct" fix per Kotlin.

- **(B) Replace `Null` with a rank-1 size-0 array literal
  everywhere:** have the parser emit `APLValue::Array(empty_rank1_array)`
  instead of `APLValue::Null` for `⍬` tokens. Same end result, but
  the literal would need to be wrapped in a constructor call
  site-by-site.

- **(C) Centralize the arrayify in the engine:** wrap the parser's
  `⍬` token AND every builtin entry in a single `arrayify()` helper
  that does `Null → KapArray::new(vec![0], …)`. This is the same
  Kotlin does internally (see `reshape.kt:249-271` and
  `math_functions.kt` scalar+scalar short-circuit), but on the Rust
  side it means threading a single `b.to_array()` call through every
  builtin that takes a "right arg". The cost is comparable to (A) —
  every dispatch site needs a normalization step.

The first part of T2.2 (this fix) does **not** choose between these
options. It just makes the two most-failing cases for `⊥` work, by
re-implementing Kotlin's local arrayify INSIDE `fn decode`. The
same trick will be needed in every other builtin that takes a
"right arg" and dispatches on rank/dimensions — see the 9 divergent
test outputs listed under point 1 above. Each is a separate
~5-line patch.

The same applies to the encode function (`fn encode` which
implements `⊤`): it ALSO needs a Null-guard (for `2 ⊤ ⍬` and
similar) and a double-promotion path (for the encode-direction
equivalent of `floatingPointArguments`, though the Kotlin test
corpus only covers the encode direction with integers). This
session did not apply those patches to `fn encode` because none of
the 31 EncodeTest cases require them.

## Notes

- **`fn decode` and `fn encode` are mis-named.** The function body
  labelled `fn decode` implements `⊥` (encode), and `fn encode`
  implements `⊤` (decode). The verb binding at
  `evaluator.rs:2918-2919` is correct (`"⊤" => self.encode(...)`,
  `"⊥" => self.decode(...)`); only the function names are inverted.
  No semantic bug, just a readability trap for new readers.

- **REPL display issue with stdlib loaded.** `standard-lib.kap`
  defines `⊤` and `⊥` as user functions calling unimplemented
  `scalarEncode`/`vectorEncode`. With stdlib, `⊤` resolves to a
  `<function>` value and the parse is wrong (`(2 2 2) ⊤ 3` displays
  as `((2 2 2) <function> 3)`). Confirmed via `--no-standard-lib`:
  `(2 2 2) ⊤ 3 → (0 1 1)` correctly. The conformance test and the
  new parity test both use `Engine::new()` (no stdlib), so the
  REPL-only issue does not affect CI. A separate task would be to
  implement `scalarEncode`/`vectorEncode` natively so the stdlib
  user functions can resolve — but that is an `io.kap`/`math.kap`
  stdlib-completion task, not a T2.2 concern.

- **Stale-binary discipline followed.** Every evaluator edit was
  followed by `cargo build -p kap-cli` (not just `-p kap-core`),
  per ROADMAP §0.1. The 3 failures that initially appeared after
  the first patch were diagnosed to the test's wrong expected
  values (port output was correct), not to the patch. The
  double-promotion patch was the only genuine correctness gap and

## [2026-08-23] Tier A CLOSED — operator-derivation parse + keyword-symbol fix (⌸/⎕A/⎕p/when all oracle-parity)

Two parser blockers remained between the native `⌸` (landed 2026-08-22) and real Tier A
acceptance via `use("base-functions.kap")` (the stdlib `⌸` def, NOT the native builtin). Both
fixed; every acceptance symbol probed side-by-side against the oracle.

### Blocker 1 — `(≠⌸)` failed to PARSE as an operator-derivation when `⌸` is a known user-op
`base-functions.kap` defines `∇ (keys) (fn ⌸) (values) {…}` so inside the file `⌸` becomes a
**known user-operator** (`known_ops.contains("⌸")`). The port's `try_parse_train` classified
`(≠⌸)` as a "symbol-list literal" and returned `None`, so the surrounding call site threw
`expected a function in train`.

**Root cause (two sub-bugs):**
- The operator-derivation block I added earlier built `Instr::OpCall` when `⌸` is a known op,
  but `is_function_expr` (and `is_definite_function`) did NOT include `OpCall`. So the
  1-member-train wrap (`funcs.len()==1 && is_function_expr(...)`) failed → `try_parse_train`
  returned `None` → parse error.
- A **keyword symbol** (namespace `== "keyword"`, e.g. `:export`) was wrongly allowed to bind
  as the *left operand* of an operator-derived member: `declare(:export ⌸)` parsed as
  `Derived{:export, ⌸}` → eval error `unknown function: keyword:export`. In Kap, `:export` is a
  declaration *value* that strands into the array `[keyword:export, ⌸]` (Kotlin treats
  `declare(:export a)` as `[Symbol{export,keyword}, Symbol{a}]`).

**Fixes (parser.rs):**
1. `is_function_expr` now matches `Instr::OpCall { .. }` (so a single `(≠⌸)` / `(f g⌸)` wraps as
   a 1-member train and applies to the surrounding `k … v`).
2. `is_definite_function` now matches `Instr::OpCall { .. }` (so 2-train chaining with a
   user-op-derived member works too).
3. The operator-derivation block bails (`funcs.push(e)` instead of binding) when the preceding
   member `e` is a keyword symbol (`matches!(e, Instr::Symbol{namespace:Some(ref ns),..} if ns=="keyword")`),
   so `:export ⌸` → `[keyword:export, ⌸]` array, never a Derived.

### Blocker 2 — `use("base-functions.kap")` now loads clean
With the keyword-symbol fix, `declare(:const (⎕A ⎕a ⎕d))` and `declare(:export ⌸)` both parse
and the file loads. `⌸` (stdlib def) is registered via `declare(:export ⌸)`.

## [2026-08-23 — ADDENDUM] Tier B STARTED — high-value stdlib slice loads; namespace + keyword fixes

Continued the roadmap into **Tier B: load `standard-lib.kap` incrementally**. The highest-value

### Bug 3 — `declare(:export ⊥)` (and any `declare(:export <redefined-primitive>)`) corrupted the parse
After `math-kap.kap` redefines `⊥`/`⊤` as user functions, `declare(:export ⊥)` was parsed as a
**2-train** `[keyword:export, ⊥]` (because `⊥` became a definite function AND `keyword:export`
was ALSO treated as definite via `namespace.is_some()`). `declare` then *called* `⊥` →
`⊥ needs two args`. Root cause: keyword-namespaced symbols (`:export`, `:const`, `:local`) were
classified as definite functions / function-expressions.

**Fixes (parser.rs):**
- `is_definite_function`: `namespace.is_some()` → `(namespace.is_some() && namespace != "keyword")`.
- `is_function_expr`: added an early `return false` for `Instr::Symbol{namespace:Some("keyword")}`.
- Net effect: a group containing a keyword symbol always strands into an `Array` (symbol list),
  never a train. `declare(:export ⊥)`, `declare(:const (⎕A ⎕a ⎕d))`, `declare(:export ⌸)` all parse.

### Bug 4 — bare `⎕A` / `unwindProtect` / `when` unresolved after `use` (namespace isolation)
Every stdlib file opens with `namespace("X")` (`kap`, `io`, `http`, …). The port's
`ns_registry.resolve_bare` only fell back to `default`, not to `kap`. After `use("standard-lib.kap")`
the chain ends in `io` ns (io.kap's `namespace("io")`), so `⎕A` (in `kap` ns) was invisible —
even though the oracle exposes `⎕A` directly after `use("standard-lib.kap")`.

**Fix (lib.rs `resolve_bare`):** added a fallback to the `kap` namespace (when it is not already
the current/imported one), mirroring the existing `default` fallback. Now bare `⎕A`, `⎕p`,
`when`, `io:print` all resolve after the high-value `use` chain.

## [2026-08-23 — ADDENDUM 3] Roadmap Tier A probe — `use("base-functions.kap")` / `⌸` investigation

Picked up the roadmap's **Tier A** (load `base-functions.kap` → `⌸`/`⎕A`/`⎕p` work). Established a
probe baseline. **Finding: most Tier-A features are ALREADY wired** (from prior Tier-A/B commits) —
only ONE genuine gap remains, and it is an operator value-reference bug, not a missing feature.

### What already works (verified on rebuilt binary)
- `use("…")` file include — loads `structure.kap`, `base-functions.kap` resolves via lib path. ✓
- `⍞` apply-reference operator (`DynamicRef`) — wired (parser.rs:2034, 2174). ✓
- `⫇` / `group` (`GroupFunction`) — wired (evaluator.rs:1723, 4437+). ✓
- `,[axis]` catenate-with-axis — `1 2 3 ,[0.5] 4 5 6 → (1 4 2 5 3 6)`. ✓
- `¨` each adverb — `dbl¨ 1 2 3 → (2 4 6)`, `2×¨ 1 2 3 → (2 4 6)`. ✓ (the earlier
  `undefined symbol: ¨` was downstream of the `use` abort, not a real gap)
- `∇ (a) { a+1 }` simple fn-def, and `∇ f (a) { a+1 }` ∇-FIRST — both parse + run. ✓
- `⎕A ← @A…@Z → "ABC…Z"`, `declare(:export (⎕p ⎕pl ⎕A ⎕a ⎕d))` — both work. ✓

### The one real gap: user-defined operator symbols are NOT referenceable as values
`base-functions.kap` line 3 defines `⌸` as an **operator** via `∇ (keys) (fn ⌸) (values) {…}`.
The def parses (`<operator>`), but **referencing the operator as a value eagerly triggers OpCall**:
- `typeof ⌸` → `error: undefined symbol: keyindex` (the body runs instead of returning the operator).
  Root cause: `⌸` is pushed into `known_ops` (parser.rs:751) at def time, so `typeof ⌸` / `⍞fn` /
  any bare reference parses `⌸` as `Instr::OpCall` with no operands → `apply_user_op` runs the body
  with empty args → body-local `keyindex ← =keys` fails (no `keys` bound).
- **Real Kap (oracle) treats operators as first-class values**: `typeof ⌸` returns the operator;
  `⍞fn¨ keyindex` applies the operand by reference; the operator is only OpCalled when used with
  operands (`data ⌸ fn`).

### Critical caveat: the ROADMAP acceptance ("loads with no errors") is NOT achievable
The oracle ITSELF errors on `base-functions.kap` **line 13**: `declare(:const (⎕A ⎕a ⎕d))` →
`Assignment to constant variable: kap:⎕A`. The oracle then **aborts the whole file at line 13**,
so `⌸` (defined lines 3-8) IS registered (callable as `data ⌸ fn`) but `⎕A`/`⎕a`/`⎕d` (lines 14-17,
after the abort) are NOT. So even on Real Kap `use("base-functions.kap")` prints errors. The port
currently dies EARLIER (it crashes on the `∇` value-reference, not the `declare(:const)`), but to
match the oracle we must (a) make operators referenceable as values, and (b) make `use` tolerate a
per-statement error and continue (like the oracle does), so the symbols defined before line 13 survive.

### Probe evidence (rebuilt binary, `--no-standard-lib` to isolate)
- `∇ (keys) (fn ⌸) (values) {…}` → `<operator>` (parses OK). `typeof ⌸` → `error: undefined symbol:
  keyindex` (body wrongly runs). Confirmed for body variants with/without `⫇`/`⍞`.
- Oracle: `use("base-functions.kap")` → `⊢ Error … : Assignment to constant variable: kap:⎕A` then
  `⊢ Error … : Operator without left function: ⌸` (because the probe called it `⌸ data`, wrong
  convention; correct is `data ⌸ fn`).

### Proposed fix scope (next chunk)
1. **Operator-as-value reference.** In `parse_apply`/`parse_primary`, a bare `known_ops` symbol should
   parse as a plain `Symbol` (value reference) UNLESS it is actually followed by a function operand
   (the OpCall form). This matches Kotlin, where `⊢ ⌸` / `⍞fn` reference the operator as a value.
   The eager-OpCall block at parser.rs:939-967 should only fire when a function operand token follows.
2. **`use` error tolerance.** `use_file`'s `eval_string_in_env` should record per-statement errors
   and continue (oracle behaviour), so one bad `declare(:const)` line doesn't abort the whole file.
3. Re-verify `data ⌸ fn` (e.g. `1 1 2 3 3 ⌸ +`) matches the oracle `⌸` result.

This is a real operator-semantics fix (not a missing primitive). See `META-INF/PROBLEM.md` for the
full blocker write-up before implementing.

## ROADMAP P1 — FINDINGS DIGEST (2026-08-23, post-M5b revert)

### What the migration proved

1. **The accumulator loop is the right architecture.** M1→M5 replaced the
   legacy parser's heuristic surface piece by piece, each step gated at 92/92
   on both paths. Every Kotlin behaviour that looked mysterious from outside
   (makeResultList unwrapping, FnParseResult continuation, close-token
   threading) turned out to have a precise line reference in parser.kt and a
   mechanical port.

2. **The oracle is the only authority.** Three times this migration, a
   "known" fact was overturned by running the JVM engine:
   - `c +` is NOT a parse error (it is a valid left-bind construction that
     fails at eval) — invalidated a test probe.
   - `(1↑⍴)` literal-first forks are built by left-bind chaining inside
     processFn, not by member-kind classification — invalidated the §10
     "free win" prediction and redirected M5.
   - makeResultList passes a SINGLE left arg UNWRAPPED (:515 resultList.first)
     — found only after `(10+) 1 → (11)` refused to explain itself.
   Rule going forward: no parser-behaviour claim without an oracle transcript.

3. **The flag gate earned its cost many times over.** The M4 axis bug
   (unconsumed `]`), the M5 wrap bug, and the M5b block-body regression were
   all caught while byte-identical default behaviour was never at risk. The
   KAP_KOTLIN_PARSER=1 env gate is the single most valuable structural
   decision of this roadmap phase.

4. **Negative results are deliverables.** M5b (block bodies → accumulator)
   regressed stdlib warnings ~10% across four files because the Kotlin path

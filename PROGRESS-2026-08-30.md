## 2. Parser gaps fixed (unblocking stdlib load)

These were PRE-EXISTING general parser bugs, surfaced when loading the vendored stdlib
(`output3.kap` uses `map:with` with `λ`-function-value pairs). Fixed to match oracle
behavior, verified with direct oracle transcripts.

- **`lexer.rs` backtick continuation** (lexer.rs:50-71): previously emitted a `Newline`
  token after `` ` ``, which broke operand attachment (`map:with \` "a" 1` parsed as a
  bare value). Now joins lines with NO separator token (Kotlin strips the backtick and
  concatenates source). Verified: `` typeToFormatter ← map:with ` `` + continuation parses.
- **`parser.rs` `λ` in strand position** (`is_strand_operand`, parser.rs:3148): `LambdaToken`
  now a strand operand. Oracle: `'a λ{⍵} 'b` → `<a function b>`, `5 λ{⍵×2} 10` → `<5 function 10>`.
- **`parser.rs` `λ` valence in `L f R`** (parse_apply dyadic block, parser.rs:2770+):
  a `λ`-reference following a value now STRIPS as a function value (→ strand) instead of a
  dyadic apply. Fixes `map:with 'kap:x λrenderY` (the `output3.kap` typeToFormatter form).
- **`parser.rs` `⍞(` dynamic function ref** (ApplyToken arm, parser.rs:471 + parse_primary
  arm, parser.rs:5211): `⍞(fnExpr)` now parses the group as a function expression
  (oracle: `⍞(+)` yields the `+` function). Handles the 3 `⍞(` occurrences in the stdlib.

### Result
`output3.kap` now parses **36/37** statements. The stdlib loads with ONE benign warning
(the lone failure, `output3.kap:323`, is the `formatInt` number-formatter display fn).

## 3. `output3.kap:323` `⍞(` gap — FIXED

- **`output3.kap:323** `res ← ⍺ ⍞((null≡renderer) ⌷ renderer λ{<⍕⍵}) v` now parses correctly.
  Root cause was `⍞(fnExpr)` (dynamic function ref from a parenthesised expression) being
  unsupported. Fixed in two `ApplyToken` arms (`parser.rs:471` top-level + `parser.rs:5211`
  `parse_primary`): the inner group is now parsed in **value context** (`parse_value_kotlin`),
  which builds the function via value-left-bind — handling a value group as an operator's left
  operand (e.g. `(null≡renderer) ⌷ …`). `output3.kap` now parses **100% cleanly** (0 parse
  errors across all 41 statements), up from failing at the first `map:with`.

## 4. Secondary gaps unmasked by the `⍞(` fix (pre-existing, separate from `map:`/`⍞(`)

Fixing the parse error meant the loader reached statements it previously never hit. Two more
pre-existing missing-feature gaps surfaced:

- **`int:registerCmd`** (`output3.kap:348`, `fhelp.kap:11`): REPL command-registration native.
  The port has no REPL command-dispatch system, so it is now a **no-op native returning Null**
  (evaluator.rs:2094, two-gate-listed at 3302) — matching the `int:libInitialised` precedent.
  This lets the stdlib load that statement without error.
- **`sysparam :renderer`** (keyword-form system parameter, e.g. `output3.kap:350`):
  `sysparam` in the port deliberately does **NOT** register keyword-form parameters (`:foo`) —
  a deliberate text-mode-build limitation (see evaluator.rs:2097). The oracle supports `:renderer`.
  This is a genuine, separate feature gap (keyword sysparams), NOT introduced by this work and
  out of scope for `map:`/the `⍞(` fix. After the `int:registerCmd` no-op, the stdlib load now
  fails on exactly this one `sysparam :renderer` statement — the last remaining blocker, and a
  distinct infrastructure gap.

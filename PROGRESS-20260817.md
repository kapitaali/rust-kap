## [2026-08-17] PHASE 15 (resumed) — Group A block-assignment, recursion/closure, assign scoping

**Bugs fixed this session (all verified by REPL probes + conformance):**

1. **`foo ⇐ { … }` (Block RHS) parsed but executed to nothing.** The uncommitted
   `OpenBrace` arm in `parse_function_atom` (parser.rs:1489) double-wrapped the body
   (`vec![parse_block_body(...)]`) and called `parse_block_body()` *after* already
   consuming `{` → `expected '{' to start block'` parse error. Fix: `self.advance();
   self.parse_block()` (returns `Instr::Block{body}` directly), matching the sibling
   `OpenBrace` handler at parser.rs:1600. `FnAssign`'s Block branch already stored a
   single `Block{Vec}` correctly, so no evaluator change was needed there.

2. **Self-recursion parsed as a TRAIN, not an application.** `parse_fn_assign` registered
   `foo` as a known function *after* parsing the body, so the body's `foo (⍵-1)` stranded
   into an `Array [foo, ⍵-1]` (returned `<function> 3`). Fix: register `name` in
   `self.known_functions` *before* parsing the RHS body (parser.rs:429 area), so a
   self-reference parses as a monadic `Apply`. `fact 5` → **120** now.

3. **Assignment leaked / mutated the wrong scope.** `Instr::Assign` used `env.define()`,
   which wrote only to the innermost env — so `n←n+1` inside a function body *shadowed*
   an outer `n` instead of updating it, and a block-local `x←9` *leaked* into the
   enclosing scope (because the old `assign` walked up parents and defined in the
   *final* root env on fallback). Fix: new `Environment::assign()` (evaluator.rs:88)
   walks up to the **nearest existing binding** and updates it in place (closure
   mutation — `n←n+1` inside `foo⇐{...}` now ups the outer `n`), and if no binding
   exists anywhere, defines in the **innermost** env (block-local `x←9` no longer leaks).
   - `x←1 ⋄ {x←x+1} 1 ⋄ x` → `2` ✓
   - `{x←9} 1 ⋄ x` → `undefined symbol: x` ✓ (no leak)

**Verification:**

- 12 hand-verified REPL cases: `foo⇐{42}`/`{⍵}`/`{⍺+⍵}` → 42/5/7; `fact 5`=120;

## [2026-08-18] `⍞` operand binding + `;` vector separator (engine fixes)

**Verified-correct, zero conformance regression (full suite still 823/176/1357/311).** Two
engine fixes, both regression-free on `cargo test -p kap-core --lib` (79 passed):

1. **`⍞` operator operand binding** (`evaluator.rs::wrap_fn`). The function operands were
   wrapped as `Apply { operand, left: ⍺, right: ⍵ }`, pre-binding each operand to the
   operator's left data `⍺`. So `⍞x 5` under `3 -foo+ 4` returned `3 - 5 = -2` instead of
   `- 5 = -5` — and a fork like `100 ⍞y a0 ⍞x a1 ⍞x b` stranded into a vector instead of
   forking. Fix: bind each operand as the *raw* function (`UserFn` whose body is the operand
   `Instr`, `split=1`; closures/blocks stored directly) so `⍞x`/`⍞y` apply to their explicit
   args exactly like Kotlin. Verified: `∇ (a0) (x foo y) b { ⍞x 5 } ⋄ 3 -foo+ 4` → `¯5`,
   `⍞y 5` → `5`; `twoArgOperator0`→`107`, `twoArgOperator1`→`108` (Kotlin ground truth).

2. **`;` as a vector/argument separator** (`parser.rs::parse_apply` both strand loops). Added
   `ListSeparator` (`;`) as a break condition alongside `at_statement_boundary()`, so
   `(10;11)` parses to `(10 11)`, matching Kotlin. Verified: `(10;11)`→`(10 11)`, `(2;11)`→`(2 11)`.

**Did NOT move the headline counts:** the 10 remaining CustomFunctionTest MISMATCH are dominated
by two deeper gaps that these fixes don't address:
- **`(a0;a1)` left-param *destructure*** in `apply_user_op` (evaluator.rs:1112): `bind_split =
  left_params.len().min(1)` slices the *flat* name list at 1, so `∇ (a0;a1) ...` binds

- **`;` inside operator *names*** should be a parse error (Kotlin `twoArgOperatorSemicolonNames`,

**Net:** engine is more correct (`;` vectors + `⍞` operands), no regressions, but the last 10

## [2026-08-18] Parse-exception validation for `∇` defs (the 9 should-error cases)

**Done (committed below).** Added parse-time validation in `parse_fn_def` so the 9 remaining
`kind:fails` CustomFunctionTest cases now error like Kotlin `ParseException` instead of
succeeding:

- `;`/`,` inside an **operator-name** component → error (`∇ (a0;a1) (x;foo;y) b {...}`,
  `∇ (x;foo) (a0;a1;a2;a3) {...}`, `∇ (x;foo;y;z) (a0;a1;a2;a3) {...}`).
- operator-name component > 3 symbols → error (`∇ (z x foo y) b {...}` / `∇ (a0;a1) (z x foo y) b {...}`).

The component collector now records `(names, used_sep)` so the multi-name-separator rule can tell
`;`-joined groups from space-joined ones. The dup check iterates all components (so 13-param dup
fires), and the name-component exemption keeps valid operators like `∇ (a0;a1) (x foo y) b {...}`
working.

## [2026-08-18] `,` is a Symbol (catenate), not a structural separator — last CFT UNSUPPORTED fixed

**The remaining UNSUPPORTED CustomFunctionTest case `f ⇐ -, ⋄ 10 f 20` is now OK.**
Result: `(¯10 ¯20)` = `(-10 -20)`, exactly matching Kotlin (`-,` is a 2-train/atop: `-(x,y)`).

**Root cause was a stale-binary trap, not an evaluator bug.** The change itself is small and was
correct from the start — the multi-turn debugging confusion came from rebuilding the wrong crate:

- `,` (comma) must be a **function Symbol** (catenate, `,`), exactly like Kotlin
  (tokeniser.kt:555 makes `,` a `Name(",",null)` single-char exported function; engine
  registers it as `ConcatenateAPLFunctionLastAxis`). It must NOT be a structural separator, and
  must NOT be absorbed into the preceding symbol.
- Changes (all committed together):
  - `lexer.rs`: removed `,` to `Token::Comma` mapping.
  - `lex_helpers.rs`: `is_symbol_start` now includes `,` (start of a symbol); `lex_symbol`
    continuation does NOT include `,` (so `-,` stays two symbols, not one).
  - `token.rs`: removed the `Comma` variant.
  - `parser.rs`: removed all 8 `Token::Comma` arms; `,` now flows through normal `Symbol`
    handling. The lambda/param-list `,` separator was converted to match
    `Symbol { name: "," }` so `(a,b)` params still parse.

**The trap:** I was running `./target/debug/kap` (built by **kap-cli**) but only building with
`cargo build -p kap-core`. `cargo build -p kap-core` rebuilds the library but does NOT rebuild
the kap-cli binary, so every probe/run hit a stale binary that never had the `,` change — hence
the spurious `undefined symbol: ,` and the long non-productive debug session. **Always build with
`cargo build -p kap-cli`** (or `cargo run`) when testing the REPL/binary. After rebuilding the
binary, `f ⇐ -, ⋄ 10 f 20` immediately returned `(¯10 ¯20)` with zero evaluator changes needed.

**Verified:** `cargo build -p kap-cli` clean; `cargo test -p kap-core --lib` 81/0 (no reg);

(parsed+evaluated). All CustomFunctionTest implemented-feature cases are now OK; the only
UNSUPPORTED/panic survivor in CFT is `∇ (a;b) () (c;d) { a+b+c+d }` (empty `()` param group
panics — a separate pre-existing gap, not the `,` case).

**Lesson to remember:** for this repo, `-p kap-core` build != the runnable binary. Use

## [2026-08-18] STRINGS branch — char arithmetic (`+`/`-` with chars/strings)

**Rules reverse-engineered from `StringsTest.kt` (asymmetric, intricate):**
- A single `Char` may **never** do arithmetic (`@a+@A`, `@a-98`, `@a±1j1`, `1j1±@a` all error).
- `Str + Number` and `Number + Str` => element-wise codepoint shift -> `Str` (both `+` directions OK).
- `Str - Number` => codepoint shift (OK); `Number - Str` => **error** (int−char asymmetry).
- `Str - Str` => element-wise codepoint **difference** -> numeric vector (e.g. `"bBa"-"aAb"`->`(1 1 -1)`).
- Doubles in the number side truncate toward zero (`"abc"+0.1 0.9 6.2`->`abi`).

**Fix:** added three helpers in `evaluator.rs` — `numbers_of` (collect numeric operand(s) of the
partner), `char_shift` (codepoint ± number -> `Str`), `char_diff` (string−string -> numbers) — and
`compute_char_op(left, right, is_add)` which returns `Some(result)` for character operands
(single-char => error; string logic as above) and `None` to fall through to ordinary `num2`. Wired
`compute_char_op` into the `+` and `-` dispatch arms **before** `num2` (must inspect left via
`lv.as_ref()` and right via `right_val.as_ref()` without moving them).

**Verified (fresh `cargo build -p kap-cli` binary):**
- `"bBa" - "aAb"`->`(1 1 ¯1)`, `"af" + 1 ¯1`->`be`, `8 ¯1 + "af"`->`ie`, `"abj" - 0 ¯11 3`->`amg`,
  `"abc" + 0.1 0.9 6.2`->`abi`, `0.2 11.9 1.1 + "abc"`->`amd`
- all six fail-cases error correctly (`@a+@A`, `@a-98`, `@a+1j1`, `1j1+@a`, `@a-1j1`, `98 200-"aj"`)

**Conformance `StringsTest.kt` (fresh `CONFORM_DUMP=1`, n=28): 25 OK / 1 MISMATCH / 2 UNSUPPORTED.**
- Remaining MISMATCH: `"bBa" - "aAb"` — our engine prints `(1 1 ¯1)` but Kotlin's stored
  expectation is `(1 1 -1)` (ASCII minus). The value `[-1]` is correct; this is a **display-glyph**
  artifact (Kap's `¯` vs Kotlin's `-`), not a logic error.
- Remaining UNSUPPORTED (2): supplementary-plane char literals (`"\uD835\uDC9F"`, `@\uD835\uDC9F`) —
